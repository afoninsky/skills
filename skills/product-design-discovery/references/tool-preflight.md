# Discovery capability preflight

Use this reference only when discovery depends on a capability whose availability is uncertain. Do not run a catalog-style preflight for ordinary synthesis from supplied or repository evidence.

## Principle

Verify the minimum capability needed to answer the actual discovery question. Prefer the project's existing tools and records. An absent optional editor, MCP, SaaS account, or preferred brand is not a limitation when another established method provides equivalent evidence.

A missing capability limits only the artifact or claim that depends on it:

- no current external access means time-sensitive facts need supplied authoritative sources or remain assumptions;
- no working runtime means observed-behavior claims remain unsupported, while source and documentation analysis may continue;
- no representative participants means no user-validation claim, while hypotheses and a study plan remain possible;
- no writable workspace means return the brief in the response rather than creating files.

## Check proportionally

1. Name the decision and evidence needed.
2. Inspect supplied materials, repository tools, research records, and available connectors before proposing anything new.
3. Probe a selected capability read-only and minimally: open the target, list the source, or run a version/help command.
4. Choose among continuing with equivalent evidence, narrowing the claim, asking for a missing input, or setting up a necessary capability.
5. Explain the consequence only when it changes the output or confidence.

When a formal suite toolchain record already exists, preserve its vocabulary: `available`, `missing-blocking`, `missing-degradable`, `unknown`, and `not-applicable`. Update it only when design-record writes are authorized and the observation is material. Do not create `design/toolchain.json` for a small request solely to record preflight.

## Setup and external actions

Before installing a tool, connecting an account, recruiting people, publishing a study, spending money, or writing to a remote design file:

- confirm the capability is necessary and no established equivalent exists;
- consult current official documentation;
- state the files, accounts, data, permissions, and rollback involved;
- obtain the required authorization;
- verify the result with the smallest real probe.

Keep credentials and sensitive participant data out of prompts, logs, screenshots, and the repository.

## Evidence boundary

Agent analysis and synthetic personas may help form hypotheses. Only appropriately gathered evidence from representative people supports audience-validation claims. Existing research remains scoped to its population, task, method, and date.
