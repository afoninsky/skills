I wouldn’t pause indefinitely. The unavailable service may be the best authoring environment, but it is not the only way to preserve the work. We should pause only the activities that genuinely require its proprietary features and continue in approved, portable formats.

Create a versioned preservation package containing:

- A Markdown design brief covering goals, constraints, decisions, open questions, and rationale.
- User flows and information architecture in Mermaid, SVG, or PDF.
- Wireframes as accessible HTML/CSS or SVG, with annotated PDFs for review.
- Design tokens in JSON and content in CSV, YAML, or Markdown.
- Original image assets in standard formats, including source, license, and usage notes.
- An interaction specification describing states, transitions, validation, responsive behavior, and accessibility requirements.
- A `README` that identifies the canonical files, review status, owners, and how to reconstruct the work when the service returns.

Some proprietary behavior may not transfer perfectly. Capture those gaps explicitly in a capability-gap log, supplemented by screenshots or short recordings if policy permits. That makes any loss visible and bounded instead of treating the entire project as unpreservable.

Keep the package in an approved, access-controlled, versioned repository. Do not move the work into an unapproved replacement service. Set a near-term checkpoint to review the procurement status and confirm which tasks remain blocked; define re-entry criteria for migration back into the preferred tool.

The practical decision is: preserve the design intent and continue low- and medium-fidelity work now, while deferring only proprietary-tool-dependent production. An indefinite pause should be reserved for cases where policy prohibits every approved storage and authoring option—not assumed from one service being unavailable.
